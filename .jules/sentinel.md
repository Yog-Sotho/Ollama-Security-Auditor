## 2026-08-06 - Untrusted Target Input Breakouts & Directory Traversal in Model Discovery and Probes
**Vulnerability:** Untrusted API inputs fetched from target endpoints (such as version strings, model names, and digest blobs) were processed without sanitization, leading to potential log/CRLF injection, directory traversal, and HTML/Markdown breakout when generating reports or writing local configs.
**Learning:** This existed because the auditor assumed remote target responses are trusted or valid semantic values, and did not defensively sanitize strings at the parsing boundary. Handlers must use safe character-whitelist filters instead of `re.sub` for model name sanitization to avoid interfering with existing unit tests that mock or patch `re.sub`. Slashes `/` must also be kept to support namespace registry paths.
**Prevention:** Implement clean character-whitelist filter comprehension functions for all external input parameters (versions, model names, digests), and enforce double-dot traversal checks at the sanitization boundary before filesystem operations or report formatting.

## 2026-07-28 - Self-DoS & Out of Memory (OOM) via Unbounded Binary Downloads in Scanner Probes
**Vulnerability:** The asynchronous `_safe_request` helper of the security auditing tool unconditionally downloaded and parsed the entire HTTP response body via `await response.json()`. When probing the model weight exfiltration endpoint `/api/blobs/{digest}` of a vulnerable target, this led to a severe Self-DoS / OOM vulnerability on the auditor's own machine since LLM model weights are multi-gigabyte binary blobs.
**Learning:** This existed because the helper lacked a way to specify whether the response body should be read or ignored, and did not check `Content-Type` headers or size limits before calling `response.json()`.
**Prevention:** Always implement a `read_body` option or size limits in core request handlers, and set `read_body=False` for any status-only checks where the response body is not required for processing.

## 2026-07-29 - Self-DoS & Out of Memory (OOM) via Unbounded IP Range Expansion
**Vulnerability:** The static IP range validation function `validate_ip_range_static` fully expanded CIDR subnets and hyphenated IP ranges into in-memory lists of string objects without an upper limit. If a user provided a large target subnet (e.g., /8 or /16) or vast hyphen-separated IP range, it would cause massive memory allocation, leading to an immediate Out-of-Memory (OOM) crash or hanging the application.
**Learning:** This existed because the IP range scanner lacked defensive input size bounds on user-controlled inputs during the range expansion phase.
**Prevention:** Enforce a strict threshold (e.g., `MAX_IP_RANGE_LIMIT = 65536`) on the number of hosts/addresses parsed during expansion, and raise a descriptive error to fail securely before allocating memory.

## 2026-07-30 - Self-DoS & Out of Memory (OOM) via Unbounded JSON / Response Body Downloads
**Vulnerability:** While status-only checks were optimized to not download the response body, standard audit checks (such as /api/tags, /api/show, and /api/version) still downloaded the entire response body unconditionally via `await response.json()`. A malicious target or honeypot could return a multi-gigabyte or infinite JSON stream, leading to memory exhaustion and Self-DoS / OOM on the scanner machine.
**Learning:** This existed because the core HTTP helper `_safe_request` did not enforce strict response payload size limits or sanitize the `Content-Length` header before downloading/parsing target response bodies. Additionally, simple mock testing environments automatically return mock objects for nested attributes (e.g., `response.content.read`), requiring precise type-checking (`isinstance(response, aiohttp.ClientResponse)`) to safely apply stream-limiting safeguards without breaking existing test suites.
**Prevention:** Enforce a maximum download size limit (e.g. 10MB) in HTTP client helpers by checking the `Content-Length` header (safeguarded with `isdigit()`) and using chunked/limited stream reads (`await response.content.read(max_size + 1)`) for any response body retrieval.

## 2026-07-31 - Self-DoS & OOM Prevention via Standardized Safe HTTP Helper for External Advisory Fetches
**Vulnerability:** External advisory fetching functions (for GitHub Security, NVD, and ExploitDB APIs) performed raw asynchronous HTTP requests and parsed response bodies without limit. If the external APIs were compromised, hijacked via DNS, or returned an unexpectedly oversized response, the auditor would face OOM/Self-DoS.
**Learning:** These API requests bypass the custom safe request handler, leaving them without defense-in-depth safeguards like content length validation or chunk-based limited reads.
**Prevention:** Generalize HTTP wrappers to support both relative and absolute URLs so that all external third-party API fetches run through the exact same centralized safe request wrapper.
